# 公交换乘满意度复测

城西公交运营中心用这套工作台比较改线前后的乘客反馈，把原始问卷、清洗依据及运营签署连到同一个线路版本。

## 业务场景

城西公交运营中心是一个虚构的城区公交团队，下设 4 个枢纽、21 条接驳线路。线网策划组拟把城西客运枢纽的 K12→M3 从北广场天桥迁到东连廊。现场服务台按调查窗口发放两轮问卷，记录统一口径的 1–5 分满意度和乘车时段。旧流程把表单汇总到工作簿，主要问题是改线和调查窗口容易串版、同一乘客会在两波重复计入、高峰和平峰配比变化会掩盖某个时段的结果。决策签署记录由调度和站务下载，用于更新站位图和班前交接表。

高峰定义为本地时间 `[07:00, 09:00)` 或 `[17:00, 19:00)`，其余为平峰。调查员按现场问卷记录选择时段，分析员缺失处置时核对原始站务班次登记。乘客码是跨两个窗口复用的匿名码，服务端用 HMAC 去重。同一版本只保留首份作为候选，重复提交可查且必须留痕剔除。

| 角色 | 主要页面 | 可写操作 |
|---|---|---|
| 运营主管 `director` | 线路版本、运营决策、乘客协助 | 建立和修改草稿、开启调查、复核通行恢复、签署结论并发布交接单、设置协助服务点及发布指引 |
| 现场调查员 `collector` | 乘客调查、乘客协助 | 登记匿名问卷、实走巡检和启用后的协助需求，提交站牌与无障碍告知凭证 |
| 数据分析员 `analyst` | 乘客调查、分层比较、乘客协助 | 核实缺失时段、留痕剔除、封存并发起分层比较，提交调度凭证并处理协助工单 |

三个角色均可查看线路方案、覆盖和结论。操作留痕仅对分析员及运营主管开放。

## 站点巡检与改线交接

- **站点换乘巡检**由现场调查员在调查开启后登记。按原路线与复测路线的窗口，记录高峰或平峰的经过日期、正常通行/临时绕行/无法通行及实走凭证。只有正常通行记录进入各波次、各时段的耗时中位数。绕行和无法通行须由主管引用同版本、同波次、同时段、日期不早于原记录的后续正常通行复查清除。复测路线有未清除项时可以计算和签署维持或另开复测，采用会被阻止。
- **改线交接与站务任务验收**在「采用改线」签署后开启。主管录入计划启用日，现场调查员提交站牌及无障碍告知凭证，分析员提交调度班前交接凭证。发布前，负责岗位可以补正凭证。三项齐备后，主管发布交接单，发布时冻结凭证。各岗位可下载包含启用日、采用路径、三项凭证和对应比较快照摘要的 JSON。
- 巡检与乘客问卷各自留档。巡检状态影响运营签署，问卷快照和统计规则保持原口径。已有采用记录可继续建立交接单。

## 改线启用与乘客协助

交接单发布后，运营主管可维护无障碍协助点、站务服务台和换乘调度岗的位置、开放状态和同时接单上限，并发布带集合点和引导话术的现场指引。指引修订新增版本，原协助单保留登记时看到的版本。计划启用日按上海时区判断。当天起，现场调查员按现行指引登记乘客所在位置和需求，现场录入请勿填写姓名、联系方式或问卷码。

| 需求 | 首选服务点 | 备用服务点 |
|---|---|---|
| 无台阶通行 | 无障碍协助点 | 站务服务台 |
| 路线问询 | 站务服务台 | 无障碍协助点 |
| 错过换乘 | 换乘调度岗 | 站务服务台 |

派单依次检查首选、备用服务点的开放状态和在办单数。两个服务点均暂停、满额或尚待设置时，需求入待派队列。调整服务点后，分析员可重新分派旧单，也可对已分派单填写办结结果并释放名额。协助单的登记、分派变化和办结均留有处理记录。并发派单按线路版本串行计算服务点容量，并发发布指引时以当前版本校验提交表单。

从线路版本选择演示线路 `NM-26A`，再打开「乘客协助」。南门 5 号港湾至地铁 B 口已有三项交接凭证和首版现场指引。无障碍协助点一席已占，站务台两席占一席，调度岗已有一份错过换乘的协助单。可在主管账号暂停无障碍点并把站务台上限降至一席，由调查员登记一份无台阶通行需求，观察待派。恢复站务台容量后，由分析员重新分派并办结。

## 离线补传与首份合并

站点断网时，调查员在离线表单上照常填写，恢复网络后按批补传。补传只在「调查执行中」的版本可用，现场调查员和数据分析员都可发起。

- **批次与续传**：以批次号和可选的应到份数建立批次。同一批次号再次提交返回原批次，继续接收；已结案批次不能复用批次号。上传按离线编号 `offline_ref` 逐条入账，同一编号重试时跳过并回报，断点续传不会重复新增已收问卷。空批次可取消，已收问卷的批次只能合并。
- **合并与首份**：合并时把本批问卷写成样本，再按匿名乘客归一。同一匿名乘客以**实际填写最早**的一份为首份：补传问卷填写时间更早时，替下已计入的那份（线上问卷沿用登记时间比较；补传问卷用原始填写时间），两份都留在档。原首份转为剔除并记录「晚到首份」依据，后到的一份记重复留档剔除。合并幂等，重复合并不新增样本。合并会同步改写此前批次的问卷去向，使其依据仍指向最终首份。
- **封存互斥**：仍有未合并批次时暂停封存，分析页会列出待合并批次并停用封存按钮；单份录入、清洗队列和巡检不受影响。批次全部结案后恢复正常封存，封存后拒绝补传。
- **去向追溯**：乘客调查页的「离线补传批次」列出每个批次的应到/已收份数、每份问卷的填写时间、去向（首份计入 / 被替下留档 / 重复留档剔除）和依据；「全部问卷」在样本号下标注来源与填写时间。操作留痕记录批次开始、接收、合并、替下与取消。

## 示例工作日

1. 08:30 主管查看 `CX-26B` 已启用的版本。基线窗口为 11 月 3–7 日，复测窗口为 11 月 10–14 日，均为 2026 年。
2. 08:40 比对北广场 3 号站台至地铁 B 口与东连廊 1 号港湾至地铁 C 口，备选版本 `CX-26C` 仍处于草稿。
3. 09:00 调查员从东连廊服务台回录匿名乘客码 `CX-NEW-011`。乘车日期为 11 月 13 日，属于复测高峰，评分 4。
4. 09:20 分析员对照《东连廊服务台班次记录》，给 `CX-049` 补录平峰。`CX-050` 对应已交首份的乘客，留痕剔除。
5. 09:30 查看高峰、平峰分组。两层分别有 12 份基线和 13 份复测，满足各波次各层至少 8 份的封存门槛。
6. 09:35 封存 50 份有效问卷。worker 计算每层 U 检验、评分分布、中位数和效应量，输出总体比较及采用门槛判定。
7. 10:00 主管签署「采用改线」，填写调度与站务的执行安排，并下载 `CX-26B-decision.json`。

## 统计口径

- 每层以改线后为参照方向。`U` 等于改线后胜过改线前的配对数加同分配对数的一半，通过平均秩计算。`2U/(n₀n₁)−1` 等于获胜比例减失败比例，取值范围为 `[-1, 1]`。
- 总体比较合并各层中心化 U，取 `w = 1/(n₀+n₁+1)`。总体效应量为 `Σ[w(2U−n₀n₁)] / Σ(wn₀n₁)`。层内和总体双侧 p 值采用同分修正的正态近似，无连续性修正。全部同分时返回 `p=1`、效应量 `0`。
- 采用规则为总体 `p ≤ 0.05`、分层效应量 `≥ 0.15`、每层效应量都 `> −0.20`。这些是模拟运营组的预设门槛。问卷基于两轮观测调查，节假日、交通和天气等窗口差异仍可能影响结果，因此只能用于相关的运营判断。
- 封存先检查清洗队列为空及四个样本格均达标。算法版本和排序后的样本号、波次、时段、评分组成 SHA-256 快照，worker 计算前再校验。封存后拒绝问卷及版本写入，签署时再检验状态和采用条件。

算法参考：[SciPy Mann–Whitney U 文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.mannwhitneyu.html) · [van Elteren 原文](https://ir.cwi.nl/pub/8192)

## 代码与数据

- `backend/migrations/001_transfer_review.sql` 定义三个领域表、约束、审计和角色表。`backend/src/schemas.py` 定义入口模型。
- `backend/migrations/002_route_delivery.sql`、`backend/src/walk_checks.py` 和 `handover.py` 负责实走巡检、复查约束、交接任务和发布留痕。
- `backend/migrations/005_offline_backfill.sql` 定义补传批次与离线问卷收件表，并给样本增加 `source / filled_at / offline_ref / merge_note`。`backend/src/backfill.py` 负责批次续传、幂等接收和首份归一，`backfill_schemas.py` 定义离线问卷入口。
- `backend/src/plans.py`、`surveys.py`、`conclusions.py` 各自承载领域 API。`analysis.py` 为计算实现，`worker.py` 领取和完成异步复测。
- `backend/scripts/seed_demo.py` 以账号邮箱、线路版本号和首次创建版本作为幂等边界。seed 重跑不修改已签署决策或清洗后的样本。
- `frontend/src/app.js` 装配路由，`state.js` 管理会话、当前版本与调查队列筛选，`api.js` 连接同源 API，`components.js` 提供公共表现及表单交互，`pages/` 负责六个业务页面。
- 共享枚举包括 `Cohort`（改线前、后）、`TimeBand`（高峰、平峰）、`Stage`（线路状态）、`SampleState`（清洗处置）、`Decision`（签署选项）和三角色。取值分别落在 `backend/src/schemas.py`（角色定义还见 `auth.py`、`seed_demo.py` 与 API 权限），数据库迁移约束和 `frontend/src/state.js`。结论状态 `queued / ready / signed` 由迁移、`conclusions.py`、`worker.py` 和分析/决策页消费。
- 巡检结果和交接任务枚举在新增迁移、`walk_checks.py` / `handover.py` 和前端对应页面定义。`CX-26B` 的首次演示 seed 包含两条正常通行记录。
- 补传去向枚举 `first / superseded / duplicate` 由迁移 `005` 约束，`backfill.py` 写入，`frontend/src/pages/backfill.js` 展示，嵌在乘客调查页。
- 乘客协助使用 `Desk` 和 `Category`（`backend/src/support_schemas.py`、`frontend/src/support-api.js`、迁移 `003` / `004`），派单原因与处理动作由 `support_dispatch.py` 记录，在 `support-api.js` 和 `pages/support-queue.js` 显示。启用状态由 `support_directory.py` 提供，由 `pages/support.js` 展示。
- 乘客协助的验收脚本、日志和截图见 `../../test-artifacts/gb-1051/min35/`。
